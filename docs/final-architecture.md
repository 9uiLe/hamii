# hamii — Current Architecture

hamii の Runtime / Editing Source of Truth は Native-semantic IR です。Human GUI と AI/automation CLI は同じ `ProjectService` へ semantic intent を送り、`MutationEngine` と `DocumentValidator` を通した結果だけを Canonical repository に保存します。

## Product boundary

hamii は Canvas、Layers、Components、Inspector、Tokens、Assets と Native UI semantics を結ぶ macOS design environment です。Networking、authentication、database、business logic、routing implementation、DI、app lifecycle は Core IR の対象ではありません。Product repository に統合するときは semantic contract と integration profile を AI に渡し、既存 architecture へ適応します。Native source は IR の正本になりません。

## IR and ownership

`Document` は自由な Page、Screen、Scope、ComponentDefinition、Token、Asset、Interaction、Motion、PreviewFixture、Target と AuthoringHarness を含みます。Page は Canvas organization であり Scope ではありません。Screen は Scope と Layer root を持ち、AppSurface は Screen を参照します。AppSurface には Target、Device、Runtime、BuildEnvironment、Fixture、Scope が別 field であります。

ArchitectureScope の依存 predicate は `owner ∈ ancestors(consumer) ∪ {consumer}` です。Component、Token、Asset の参照に同じ rule を適用します。Component availability は nested Definition にも再帰的に適用し、Picker、SQLite projection、Mutation Validator が共通 evaluator を使います。ComponentDefinition の owner は Variant に移せません。Instance は Definition ID、variant selection、property/slot value、public override のみ保持し、解決結果は永続化しません。`ComponentResolver` は選択 variant の衝突と private override を拒否します。Promotion candidate は consumer Scope の Least Common Ancestor です。Agent の Scope promotion は profile で明示的に許可されない限り拒否します。

Layer は stable ID、kind 別の `LayerPayload`、hierarchy、layout、accessibility、native intent、target override を持ちます。実装済み payload は Stack、Text、Image、Button、Component Instance、Scroll、Overlay です。Text の値と binding、Button の label と任意 event、Image の任意 asset reference、Component Instance の参照は各 payload が所有します。現行 Canonical Format v2 は kind 固有の flat Layer keys と順序付き `effects` を保存します。実装済み effect は spacing Token を参照する `padding` です。旧 `layout.paddingTokenID` と他 kind 用 field は Current Layer が拒否します。Canvas と macOS Native Preview は effects を記載順に適用し、Generator は未実装 effect を明示的に拒否します。Typed target extension など残る production lowering は [Native-semantic IR ADR](../adr/native-semantic-ir/ADR.md) の実装対象です。System UI を自由配置 Rectangle として保存する設計は採用しません。

`CapabilityDeclaration` は target ごとに `Exact`、`Portable`、`Target-specific`、`Approximate`、`Unsupported`、`External Integration Required` を表します。Current IR から `SemanticRequirementExtractor` が Preview 固有の fixture availability と分離して意味単位の要求を取り出し、`CapabilityEvaluator` が target/platform/framework/runtime の Profile と宣言を評価して `CapabilityLossReport` を作ります。`TargetPlanner` と `SwiftUIGenerator` は同じ抽出器と evaluator を使い、それぞれの実装済み意味を別 catalog で制限します。Generator は AppSurface を受けず runtime を未指定として評価します。Runtime 固有と宣言された意味は未指定 profile で許可しません。未宣言・未実装の意味は Unsupported で拒否し、承認済み Approximate も loss として残します。既存の node key は対応する basic visual semantics だけの fallback であり、同じ意味の明示宣言が優先します。event、binding、asset source、toolbar の独立した意味へ暗黙拡張しません。`effect.padding` は独立した明示宣言を要求し、`token.spacing` から継承しません。[Capability ADR](../adr/capability-contract/ADR.md) は残る consumer 接続と framework coverage 検証を管理します。

## Mutation and authoring

Human/Agent adapter は `AuthoringIntent` を `ProjectService` に渡します。Service は client が観測した opaque な `ClientPrecondition` を現在の Canonical observation と照合し、MutationEngine が candidate Document と `SemanticPatch` を作成します。DocumentValidator が ID、参照、Scope、Component、Token、Asset、Interaction、Harness rule を検証し、失敗した candidate は保存しません。同値編集は revision を進めず Canonical files を書かず、同じ precondition を返します。Patch は entity ID、property path、old/new value を持ちます。GUI と CLI は同じ service を使用します。`DocumentRevision` は MutationEngine 内の順序検査に残しますが、client state identity の代わりにはしません。

AgentHarness は profile 名、mutation limit、Scope promotion 権限を持ち、`hamii-agent-profiles.json` に独立 version で保存します。`builder` と読み取り専用 `reviewer` を作成時に登録します。HumanHarness は snap と insertion preference を持つ actor 設定です。両者は Product rule を変更できません。AuthoringHarness は現在、control label、token spacing、atomic mutation count の machine-readable rule を持ちます。Policy の拡張と waiver は [Authoring Policy ADR](../adr/authoring-policy-enforcement/ADR.md) の検証対象です。Skill text は操作方法の説明であり、権限判定ではありません。

## Persistence, query, migration

Git に置く `hamii.json` と entity ごとの JSON が Canonical Data です。Stable ID は filename と reference の両方に使います。`hamii.json` の revision は hamii semantic mutation の順序と journal の旧新判定に使います。これは Canonical contents の identity ではありません。Document、Authoring Harness、Integration Profile の format version は独立 field です。Current Format 以外は `HamiiFormat` の version gate で拒否します。Current Core は historical parser を持ちません。Current Format v2 は entity-per-file です。Screen JSON はその Screen の完全な Layer tree、ComponentDefinition JSON は完全な definition Layer tree を所有します。Layer tree は所有 entity の JSON 内に保存します。Page は Canvas organization と AppSurface の配置を表し、AppSurface が独立した Screen を参照します。Canonical shard 粒度と read optimization は別の責務です。Authoring と currentness の保証には、完全に検証された coordinated Canonical observation を使用します。Read-only semantic slice には Project 全体の妥当性や mutation の許可を与えません。

`CanonicalSnapshot` は `WorktreeCoordinator` の lock 内で root 基準の Canonical JSON path を列挙・symlink 検査し、keyed `String <` 順に各 file の bytes を一度だけ捕捉します。Manifest、entity shards、Agent profiles の decode / validation と Snapshot identity は同じ捕捉 bytes を使います。Entity array は folder ごとの `lastPathComponent` 順です。Identity は相対 path と exact bytes の length-prefixed SHA-256 であり、JSON の意味が同じでも bytes が変われば別 identity になります。Repository Asset blob は JSON capture に含めず、Document validation 時に別途 integrity を検査します。Git freshness oracle と ClientPrecondition はこの Snapshot 取得とは別の責務です。

`HamiiFormat` の `WorktreeCoordinator` が `.hamii/write.lock` と local observation epoch を所有します。Canonical Repository はその境界内で journal 回復・観測・保存を行います。保存時には読み込み時点の Document から期待 Canonical bytes を組み立て、現在 bytes と照合します。不一致なら journal 作成前に conflict として中断します。変更された shard の旧新 bytes を `.hamii/transaction.ready` に journal として準備し、Canonical shard を更新してから `hamii.json` の revision を最後に切り替えます。次の `load` / `save` は journal を先に復旧し、manifest が旧版なら rollback、新版なら roll forward します。適用時に旧新 bytes 以外を観測した場合は conflict を返し、その bytes と journal を保持します。処理済み journal は rename 後に削除するため、cleanup 中の停止でも完全な revision を開けます。現行 `.hamii/write.lock` は hamii process 同士の協調用です。journal は hamii save の停止復旧用であり、観測されない外部書込を復元しません。検知できた競合は保存中断へ倒します。check と replace の間に入る外部書込を現行実装が必ず検知する保証はありません。停電耐久性は [Power-loss ADR](../adr/canonical-power-loss-durability/ADR.md) の検証対象です。

### Canonical collaboration contract

`.hamii/canonical-generation.json` は同じ worktree lock の下で更新する coordination state です。`CanonicalGeneration` は lineage と遷移番号を持ち、Snapshot identity、client precondition、Index generation ID とは別です。通常 save は Canonical shard に触る前に Pending を記録し、journal 回復後の Snapshot が旧状態または期待する新状態に一致する場合だけ Stable に戻します。Managed switch と validated merge publication も既存の pending gate と検証済み Snapshot に世代を結び付けます。初回 create は最初の検証済み Snapshot から Stable を作り、既存 Project で record が欠けた場合は lock 内の full parse / validation 後に新しい lineage を確立します。破損または不明な状態を推測で確定しません。Query は検証済み Index source binding と組み合わせる場合だけ、この世代を Safe Fast Path の条件として使います。

一つの worktree は一つの coordinated writer domain です。hamii GUI、hamii CLI / AI、hamii-managed Git operation が同じ worktree を変更するときは共通の lock、generation、recovery、validation を通します。raw Git CLI、外部 editor / script / AI など非協調 writer による同一 worktree 直接変更は安全な共同編集経路として保証しません。外部変更の検知は defense-in-depth です。独立 writer は別 branch / worktree で作業します。

`hamii git switch BRANCH --state TOKEN` は、clean な worktree で `WorktreeCoordinator` の lock を取得し、client epoch を先に更新して pending marker を置き、Git switch 後に Canonical validation を行います。Pending 中は通常の Canonical access を拒否します。`hamii git recover` は source または target の既知 HEAD、clean worktree、valid Canonical state が揃った場合のみ pending を解除します。Partial Git state は fail closed です。Raw Git CLI は managed operation ではありません。`hamii git merge check BRANCH --state TOKEN` は一時 worktree に merge candidate を作り、Canonical parse・schema・stable ID・reference・Scope / Component・Authoring rule と一時 Index rebuild を検証します。Source worktree と公開 Index は変更しません。Git merge exit 0 は hamii merge success ではありません。失敗時は candidate を拒否し、両側の有効な branch / worktree を保持します。

`hamii git merge publish BRANCH --state TOKEN` は `ValidatedMergePublisher` が source worktree の lock 外で immutable candidate commit を検証し、保持用 Git ref に固定します。Lock 内で source / target OID と client observation を再確認し、client epoch を失効させて pending record を置きます。Source ref の expected OID から candidate OID への CAS が Canonical publication の commit point です。その後 candidate から worktree を materialize し、Canonical identity を照合し、Repository 外の SQLite Index を別ファイルに full rebuild して公開・検証してから gate を解除します。Pending 中は observe・mutation・query・Preview mutation を拒否します。`hamii git recover` は ref が old OID なら旧状態を維持し、candidate OID なら candidate へ roll-forward して再検証・再索引し、どちらでもなければ gate を維持します。Git の ref lock または index lock が残る場合、その所有者を pending record だけから証明できないため lock を自動削除せず、gate を維持して回復を拒否します。確認済みの停止 process が残した lock は、所有者を確認したうえで別途除去してから recovery を再実行します。Index failure で Canonical ref は rollback しません。これは process crash に対する実装であり、停電耐久性は [Power-loss ADR](../adr/canonical-power-loss-durability/ADR.md) の検証対象です。

`DocumentRevision` は hamii mutation の順序、Canonical state identity は観測した contents の同一性、worktree generation は協調 writer domain 内の transition、Index generation は公開済みの derived snapshot、client session token は client の観測基点を表します。同じ token で実装できる可能性はありますが、概念は別です。`ClientPrecondition` は worktree path、coordinated local epoch、現在の Canonical JSON path/bytes を結び付けた opaque value です。Agent profile JSON も計算対象です。`ProjectService` が GUI と CLI に同じ照合を適用し、同じ revision の別 contents を拒否します。`.hamii/client-observation-epoch` は Git に保存せず、hamii save と managed Git transition の前に更新します。Process restart では journal 回復後に再観測し、epoch の欠損で旧 token を失効、破損時は client observation / mutation を拒否します。Raw Git 等の protocol 非参加 writer による無通知 A → B → A は保証外です。Undo / Redo base の連携は [Canonical state precondition ADR](../adr/canonical-state-precondition/ADR.md) の実装待ちです。

Repository Asset の blob は `assets/blobs/<sha256>` に置き、Asset entity は source path と content hash を持ちます。同じ content は同じ blob を共有します。CLI の `asset import ... --storage git` が取り込み、Canonical validation は欠落と hash 不一致を拒否します。Import の blob 書込後に mutation が競合で拒否された場合、未参照 blob が残ることがあります。未参照 blob の GC は未実装で、参照を検証せず削除しません。Remote Asset は URL が正本、Runtime-bound Asset は binding が正本で、Preview Fixture とは別です。Large binary の Git/LFS 境界は [Asset ADR](../adr/asset-storage-policy/ADR.md) の判断待ちです。Derived cache は Git に置きません。

Local SQLite は Git に保存しない削除可能な Materialized Query View です。`~/Library/Application Support/hamii/indexes/` の Document ID と worktree path から導いた別領域に `index.sqlite` を置きます。`IndexProjection` が coordinated `CanonicalSnapshot` の Document から component、usage、scope closure、availability の行を導出します。SQLite schema 8 は rows、source Snapshot identity、`IndexGenerationID`、`CanonicalRevision`、必須の `IndexSourceGenerationBinding` を同じ transaction に保存します。Binding は `Bound(G)` または `ExplicitlyUnbound` であり、key 欠損・空文字列・不正値は検索を拒否します。同じ Snapshot を再構築しても Index generation ID は変わります。Index schema 変更時は Canonical Data から再生成し、長期 migration は保持しません。

`IndexQuerySession` は process ごとに `Unknown` から始まります。初回 Query は `WorktreeCoordinator` の lock 内で journal recovery、Ready gate、coherent Snapshot、Stable CanonicalGeneration、Index descriptor と Git freshness oracle を照合します。`Bound(G)` が一致した場合は rows と process-local witness を得ます。次回以降は同じ lock 内で shared generation と現在の Index descriptor を witness と比較し、SQLite rows を読み終えるまで lock を維持します。Index file の置換後に古い SQLite connection を新世代として再利用しません。Canonical generation が変われば古い Index を拒否し、Index generation ID だけが変われば slow verification で witness を再発行します。CLI は command ごとに新 process なので、各 Query は cold verification から始まります。Warm Fast Path の性能値を one-shot CLI の値として扱いません。

Safe Fast Path は長寿命 `IndexQuerySession` の consumer が利用できます。現在の Editor の Component 一覧は `ProjectService.availableComponents` を使用し、SQLite Query session はまだ利用していません。Project を閉じたら witness を破棄し、再度開くと cold slow verification から始めます。

外部編集後に明示的に再構築した Index が `ExplicitlyUnbound` の場合、exact Snapshot identity と Git oracle がその呼び出しで current を確認できれば rows を返しますが、witness は発行せず次回も slow verification を行います。Index rebuild は CanonicalGeneration を進めません。`CanonicalRevision` は Canonical Data の状態を識別する契約であり Git commit の別名ではありません。現行 Git calculator は通常、最初の `status --porcelain=v2 --branch`、全 tracked Canonical path と index flag の `ls-files -v`、`check-attr filter`、最後の `status` という4回の Git 実行を使用します。変更を報告された Canonical path の working bytes を identity に含め、両 `status` の出力が異なる場合や flag / filter が検証不能な場合は Query を拒否します。各観測は単一の atomic Git metadata snapshot ではありません。Flag / filter の観測後に非協調 writer が変更した metadata を、最後の Git status 比較だけでは検知できない場合があります。Canonical files が同じでも HEAD 変更で保守的に失効する余地は残ります。非協調 writer に対する絶対的な同時書込保証はありません。鮮度証明は `IndexQuerySession` が担います。

`IndexRecoveryService` は、Ready gate、Stable CanonicalGeneration、同一 identity の CanonicalSnapshot、検証可能な Git revision が揃う場合だけ、missing / obsolete / malformed / corrupt / stale Bound Index を自動 full rebuild します。公開 Index は read-only に分類し、Query 用 open は既存 DB を作成・再生成しません。失敗した初回 Query が同じ coordinated lock 内で Snapshot、世代、Git revision、公開 Index state を確認できた場合は、その観測を一回の復旧にだけ渡します。観測を渡せない場合は Recovery Phase 1 が独立した lock 内で同じ条件を確認します。別 SQLite file を同じ filesystem 上に構築・検証し、Phase 2 の lock 内で世代、Snapshot identity、Git revision、公開 state を再照合して atomic に公開します。他 process が同じ source の valid generation を先に公開した場合は再利用します。公開後の proof は rows を直接許可せず、Query retry が改めて lock を取得し、Stable generation と公開 Index descriptor を再確認してから同じ lock 下で rows を読みます。Index generation が別 process に置換された場合は slow verification に戻ります。復旧と Query retry は各1回に制限します。Canonical state が不明・pending、Git source が検証不能、検知した非協調外部編集、`ExplicitlyUnbound` の source change、storage failure の場合は自動復旧せず、検索結果を返しません。外部編集後の明示的 `hamii index rebuild` は残ります。現行の自動復旧は検証済み CanonicalSnapshot から Index 全体を再構築します。増分再索引は production protocol に含めません。大規模 Project の性能は [Index recovery performance](index-recovery-performance.md) の測定条件の範囲で評価します。Merge publication は candidate と同一 Snapshot から別ファイルに full rebuild し、公開後の generation ID と source identity を照合して pending gate を解除します。

Document Format v2 が唯一の Current Canonical Format です。v1 repository は Current reader が拒否します。`HamiiMigrations` は Core/Format/Index を import せず、raw Canonical bytes を受ける v1→v2 edge を持ちます。両 document marker が 1/1 のときだけ変換し、Current の 2/2 は no-op、その他の path は拒否します。Edge は全 Layer tree の v1 padding を順序付き `effects` へ写し、必要な `effect.padding` capability を既存 `token.spacing` declaration から明示的に合成します。既知の複数 `token.spacing` 宣言と cross-kind residual は、明示的な typed resolution がなければ blocker です。未知の historical meaning と既存の `effect.padding` declaration は候補0件の hard block です。変更しない shard と blob は元 bytes を保ちます。`hamii migrate plan --json` は edge の可否と blocker を読み取り専用で返し、未復旧 Canonical journal も拒否します。

`hamii migrate prepare --json` は clean committed symbolic branch の exact source ref/OID を記録し、その OID から detached worktree を作ります。`HamiiMigrationRuntime` が production edge の変更 path だけを適用し、実 Current v2 reader・semantic/asset validation、candidate commit 後の同一 CanonicalSnapshot、外部一時領域での fresh Index rebuild を検証します。期待 path と Git diff が一致し、source ref・tree・Canonical revision が現在も一致する場合だけ、candidate OID を create-only retention ref に保持して review package を返します。Candidate tree OID は再実行で決定的です。Source branch、source Index、client epoch は更新しません。Review package は local durable record に保存します。`migrate publish REVIEW_ID SOURCE_OID CANDIDATE_OID` は candidate ref / parent / tree / diff、実 Current v2 Snapshot、一時 Index を再検証し、WorktreeCoordinator の pending gate と client epoch 失効の後に source ref を exact-OID CAS で公開します。CAS が Canonical commit point です。Candidate を materialize して Current v2 と Index の同一 Snapshot / generation binding を検証してから gate を解除します。`migrate recover` は ref が old なら旧 state を保持し、candidate なら roll-forward、neither なら gate を保持します。Index failure では Canonical を rollback しません。SIGKILL の停止復旧と停電耐久性は別の保証です。`migrate resolution --json` は clean committed v1 source の exact OID と Canonical byte identity に束縛した診断・有限候補を返します。`migrate prepare --resolution PATH --json` は未知・未解決 item を拒否し、既知選択から deterministic candidate を作ります。異なる spacing 宣言の除外や既知 cross-kind residual の破棄は exact path/value を review に残し、`potentiallyLossy` として扱います。完全同等の重複正規化は `losslessWithNormalization` です。Version 2 review record は manifest・decisions・losses を保持し、publisher は pending 開始前に同じ source から再計算して record と immutable candidate bytes を照合します。公開後も resolution audit は `.hamii/migration-reviews/` に残ります。Version 1 の自動 lossless review は従来どおり利用できます。停電耐久性の未解決事項は [Power-loss ADR](../adr/canonical-power-loss-durability/ADR.md) が扱います。

## Canvas, Preview, generation, integration

macOS Canvas は編集用 SwiftUI view です。Native Preview は対象 OS が描画する別 runtime とします。`HamiiPreviewProtocol` は Document・Surface・state precondition の snapshot、base/new state と revision を分けた patch、適用 revision/state 付き acknowledgement を定義します。欠番 patch は拒否し、snapshot で再同期できます。`HamiiNativeRuntime` は macOS SwiftUI AppSurface の supported subset を実 OS 上で描き、Text value patch を compile なしで反映します。Spacing Token の literal / alias は Canvas と Native Preview の Stack spacing / container padding へ解決し、`token.spacing` capability を要求します。`Instant Patch`、`Runtime Reconciliation`、`Component Build`、`Full Build` を区別し、build が必要な patch を compile-free path で受け付けません。iOS Simulator Host と transport は [Preview Host ADR](../adr/preview-host-transport/ADR.md)、SwiftUI state reconciliation は [Reconciliation ADR](../adr/swiftui-reconciliation/ADR.md) で検証中です。現在の Simulator boot failure は Host install 前に生じる独立した検証環境 blocker であり、transport の評価結果ではありません。iOS Native Host と product repository 変更 adapter は未実装です。

`HamiiGeneration` は対応した静的 SwiftUI subset を決定的に出力します。Binding、interaction、token lowering など未対応 semantics は error にし、曖昧な source を出しません。`HamiiIntegration` は Screen の input/event/token/asset/native/accessibility contract と repository profile を分離し、未知 mapping を unresolved として返します。AI による product repository 変更と build/test review は [Product Integration ADR](../adr/product-integration-contract/ADR.md) の実証対象です。hamii IR に TCA、MVVM、Router、DI を入れません。

## CLI and development contract

`hamii` は唯一の AI/automation interface です。主要 command は `--json` を提供します。Skill discovery は `skills list` / `skills get` で、内容は binary と同じ version です。Mutation は `inspect` または直前の mutation で得た `statePrecondition.rawValue` を `--state TOKEN` として渡し、古い state は conflict category で拒否します。Validation error は diagnostic rule です。Error と exit schema は [CLI Error ADR](../adr/cli-error-contract/ADR.md) で検証します。

CLI の taxonomy は resource-oriented authoring と query / preview / integration / generation / migration / Git の semantic namespaces を組み合わせる hybrid です。Existing production command names は安定した契約です。AI は global resource/verb/task grammar を推測せず、installed live skills から exact commands を発見します。新 command は近い existing semantic/resource namespace を拡張し、cross-resource operation に一律の grammar rewrite を強制しません。Production rename は変更・migration cost を正当化する新しい具体的 Evidence を必要とします。

`HamiiApplication.ProjectContextService` は semantic AI context の read projection です。Project summary、選択 Layer detail、Scope-aware な Component / Token / Asset summary と必要な Component / Token detail を段階的に返します。各呼出しは一つの `ProjectObservation` から投影し、`ClientPrecondition` と `DocumentRevision` を別々に返します。後続の `query context ... --state TOKEN` が現在の observation と一致しない場合、payload を返さず `conflict` とします。利用可否は `ProjectService` と同じ `ScopeEvaluator` / `ComponentAvailability` に従い、Resource list は Scope filtering の後に name と stable ID で整列して上限を適用します。Index row は利用可否の正本ではありません。Mutation は引き続き `ProjectService` を使います。`skills get context` は staged retrieval を案内します。[Production Query measurement](ai-context-query-performance.md) は payload と service / CLI 待ち時間を別々に示し、AI 総トークンは未計測です。

`ProjectContextReadSession` は process-local な Application core です。開始時に完全に検証された一つの `ProjectObservation` S0 から初回 summary を生成します。後続の Layer / Resource / Component / Token 応答は、`CanonicalRepository.verifyCurrent` が coordinated Ready boundary 内で journal を回復し、既存の exact `ClientPrecondition` 計算で S0 を検証した場合だけ、同じ純粋 projection から生成します。検証不能・不一致・pending では payload を返さず session を永久に失効させます。Session は request 間に worktree lock を保持せず、再起動時に残りません。Mutation は常に `ProjectService` が `expectedState` を再検証します。CLI の `query context session --json` は一つの process 内で初回 summary と stdin / stdout の NDJSON follow-up を提供します。`usage` / `notFound` は session を維持し、freshness / storage failure は structured terminal error で process を終了します。入力は一行 64 KiB に制限し、session registry / daemon / disk cache は持ちません。one-shot CLI は各応答で独立した Canonical observation を行います。[Context session contract](context-session.md) に request schema と再開手順を記載しています。[Release comparison](context-session-performance.md) は同じ payload と freshness 保証の下で retrieval latency を比較し、AI 総トークンとは区別します。

`preview plan SURFACE_ID --json` は Target capability と Screen semantics の適合を確認します。Plan の成功は対象 OS の Host が利用可能であることを意味しません。Starter sample の macOS Surface は sample validation で plan を検査します。

`bash scripts/check.sh` が Swift 6.4 build/test、dependency check、ADR schema、CLI smoke test を実行します。CI はこの入口を使います。未解決の設計判断と検証結果は ADR queue に示します。
