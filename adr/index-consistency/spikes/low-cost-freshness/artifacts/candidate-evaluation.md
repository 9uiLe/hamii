# Canonical freshness candidates — evidence matrix

All numbers are local measurements, not a product SLA. The semantic requirement is to identify the hamii-visible Canonical Data state. A changed Git commit alone is not a semantic change. `IndexGeneration` identifies a published derived snapshot separately.

| Evaluation axis | Current guarded Git calculator | Direct-child double byte scan prototype | Size/mtime fast-path prototype | Two-stage fast/slow path |
| --- | --- | --- | --- | --- |
| Correctness | Sequential tested edits detected or rejected; one mid-query branch switch rejected | Sequential tested edits detected; loader direct/nested path cases aligned after prototype correction | Fails same-size edit with restored mtime | No safe `certainly current` predicate demonstrated |
| False negative risk | No observed miss in tested cases; last-check-to-return window and arbitrary concurrent writer remain unknown | **Confirmed:** two passes can accept a digest for a multi-file state that never existed | **Confirmed:** restored-mtime edit returns old identity | Must reject/slow-verify whenever fast evidence is not conclusive; proof for a useful `yes` path is missing |
| False positive invalidation | Canonical-unchanged unrelated commit changes HEAD and invalidates | Unrelated commit did not change tested identity; symlink/enumeration edge cases unresolved | Unrelated commit did not change tested identity | Depends on fast predicate and slow verifier, both undecided |
| Query-time cost | 8-shard in-process p95 410.47 ms; CLI fresh query p95 418.61 ms | 8-shard in-process p95 3.67 ms; 5000-shard p95 1575.92 ms | 8-shard p95 1.32 ms but unsafe | No end-to-end measurement; current Git verifier can serve as conservative slow path |
| Rebuild-time cost | Starter CLI full rebuild p95 1316.33 ms, 20 runs | Not measured end-to-end; a safe snapshot protocol would add cost | Not eligible as sole source identity | Not measured; source verification plus projection plus publication must all be included |
| Branch switch | Sequential change detected; deterministic query switch after row read returns stale; final-check gap unknown | Sequential change detected; concurrent multi-file scan has counterexample | Sequential change detected in fixture; restored metadata may hide content | Must downgrade uncertain/switching source to slow verification or stale; untested |
| External edit | Sequential staged/unstaged/untracked changes observed, hidden states rejected | Working bytes observed in sequential fixture; concurrent writer can yield impossible snapshot | Restored metadata edit missed | Watcher/cache resynchronization protocol unknown |
| Git filter / hidden flags | Tracked filter and flags rejected; no stale hit in replayed cases | Actual bytes changes observed without Git transformation | May observe ordinary edit; false negative remains possible | Fast predicate must not trust Git's transformed representation alone |
| Large-project scaling | 5000 tiny clean files p95 373.98 ms in-process; other repository shapes unmeasured | 5000 tiny files p95 1575.92 ms; file-open count dominates as an inference | 5000 tiny files p95 701.19 ms but unsafe | No benchmark |
| Implementation complexity | Four Git subprocesses, path/status/attribute parsing and race guard | Short code, but coherent multi-file snapshot needs an additional protocol | Simple code, fails the safety gate | Highest uncertainty: trusted event fence, overflow recovery, source snapshot and retry rules require proof |

The in-process candidate benchmark excludes CLI startup, SQLite, projection and rebuild. The generation SQL benchmark in the [incremental Spike](../../incremental-reindex/SPIKE.md) uses actual `IndexProjection` rows but excludes Canonical loading and revision calculation. No final calculator or recovery path is selected.
