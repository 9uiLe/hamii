# Observation shape × observation count

## Conditions

[Raw matrix and samples](observation-shape-matrix.json) were generated by `python3 scripts/measure-shard-observation-shapes.py --output adr/git-canonical-sharding/spikes/shard-merge-benchmark/artifacts/observation-shape-matrix.json`. The script creates disposable Git projects, uses semantic CLI mutations for the common base, then constructs L/S/C Canonical shards and validates each with `hamii validate`. The same Scope hierarchy, selected Text Layer, available Commerce Component, unavailable Account Component, spacing Token, AppSurface, iOS SwiftUI Target, and capability declaration are cloned into all shapes. Additional Layers are simple Text. This is a debug-build, warm local-filesystem measurement on the platform and Swift version recorded in the JSON, not a release or cold-cache benchmark.

Each shape has **10,002 total Layers**. L has one 10,000-Layer selected Screen plus two baseline Component roots. S has 100 Screens of 100 Layers each plus the two roots. C keeps the two-Layer selected Screen and the two baseline roots, then distributes 9,998 Layers across 100 additional ComponentDefinitions. The matrix records exact Canonical file count, bytes, largest shard, and median shard. L/S/C total Canonical bytes are 2,832,248 / 2,887,615 / 2,913,736 (about 2.9% spread); path counts are 12 / 111 / 112.

There are 20 ordinary `CanonicalRepository.observe()` samples and 20 instrumented samples per shape, 20 test-only single-observation candidate samples per task and shape, and 5 current one-shot CLI workflow samples per task and shape. The candidate performs one real `observe()`, then runs the same production `ProjectContextService` projections through a fixed in-memory repository, immediately, without holding the worktree lock through any AI thinking. Every candidate response matches the corresponding production CLI `context` JSON and shares one `ContextObservation`. Response bytes include CLI envelopes and are in the raw matrix. They are not AI token measurements.

Ordinary `observe()` min/max are L 108.853–114.563, S 120.604–123.084, C 121.648–125.446 ms. The raw artifact contains all other min/max and samples. Nested stage values are not added as disjoint contributions. Entity decode shifts from Screen to Component files in C; its total and Document validation remain close across these shapes. The many-file path and second read costs increase, but the ordinary observation median ratio is only **1.116**, below the precommitted 1.5 shard-routing threshold.

For every shape, T2 and T3 candidate medians are at most half the current multi-process workflow medians, and candidate payloads match. The precommitted batch criterion passes. With L as the primary existing large-Screen case, `batchSaving` for T2 is 490.257 − 108.783 = **381.474 ms**; `shapeSaving` is 122.001 − 109.364 = **12.637 ms**. Thus the routing result is **batch investigation first**. These are test-only candidate differences, not realized production savings. They combine fewer Canonical observations with fewer CLI process starts and therefore do not isolate one cause perfectly.

This phase does not decide Canonical shard granularity. Save, Git diff/merge conflict behavior, 50k Layer scale, partial load, cold cache, release performance, real project mix, AI task success, total AI tokens, and model cost remain unmeasured. No production cache, batch command, reader, session, file format, freshness rule, or Scope rule was changed. A separate batch/read-session Decision Boundary is the next investigation indicated by the committed routing rule; production adoption requires its own correctness evidence.
