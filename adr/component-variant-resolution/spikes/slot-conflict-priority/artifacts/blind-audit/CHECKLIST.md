# Independent audit checklist: slot conflict priority

This checklist was fixed before reading this Spike's A/B probes or results. It uses the [component decision](../../../../ADR.md), the [prior slot-boundary Spike](../../../slot-write-conflict-boundary/SPIKE.md), and current `ComponentResolver`, `DocumentValidator`, `ProjectService`, and `CanonicalRepository` source. Test-only behavior is evidence about a candidate, never a production rule.

## Inputs and evidence handling

- Read exact probe source, raw result, invocation, and source revision. Verify every claimed outcome against the fixture and assertion rather than the case name or summary.
- Separate current production Resolver/Validator/Repository outcomes from test-only preflight, candidate evaluator, or synthetic repository behavior. A passing prototype is not implementation evidence.
- Identify which observation is made before or after `ProjectService.mutate`, `DocumentValidator.validate`, `CanonicalRepository.commit`, and reopening. Record diagnostics, revision, ClientPrecondition, Canonical path→bytes, and attempted mutation.

## Gates

1. **Existing error preservation and priority.** Test the slot-collision candidate together with non-public `allowedOverride`, two selected Variants writing one path, unknown Variant/property/slot/path, and invalid Definition API path. A new slot diagnostic must not silently convert an invalid candidate into success. Distinguish error preservation from error priority; a new error emitted first can obscure the existing one even when both would reject. Record exact typed Resolver errors and `DocumentValidator` rules.
2. **Allowed override unchanged.** Test a public override to a slot descendant removed by replacement and a public override outside the slot. Also test a non-public descendant override. Determine whether any candidate scheme drops, rewrites, or accepts these values before public API checks; compare full resolved result or all affected fields. Confirm the current post-slot `unknownPath` behavior separately from a proposed conflict rule.
3. **Unselected Variant and negative controls.** A selected Variant writing a removed child should be classified differently from a dormant Variant with the same write. The dormant case needs an observable control where its target survives; if the slot removes the target, absence alone cannot prove the Variant was skipped. Include a disjoint selected write that must survive. Do not classify a Definition's Variant as active just because it exists.
4. **Strict ancestry.** Resolve `<stable-id>.text` against exact Layer IDs in the Definition tree. Check target itself (distance zero), strict descendant, ancestor, sibling, similarly prefixed but distinct ID, and unrelated path. Slot replacement changes a container's children, not its own identity or payload. An unsupported text write on a container is a validation failure, not a valid slot-write conflict.
5. **All nested selected slots and order stability.** When inner and outer slots both contain the target, identify the complete set of selected slots that would remove the write, not only a shortest-distance owner. Test at least two slot-name orders or declaration orders, including the case where outer replacement removes inner target before its turn. A result's diagnostic category and relevant ownership information should be deterministic; do not infer stable precedence from one ordering.
6. **Product mutation and persistence.** For a rejected candidate, use the common `ProjectService.mutate` route where reachable and verify the error, unchanged Canonical path→bytes, and unchanged persisted Document revision. Check whether the client's old precondition is still valid or explicitly report an epoch change; do not infer token stability from byte equality. Verify accepted controls reopen correctly. If the required mutation cannot be expressed by current public intents, label direct Repository tests as infrastructure evidence only.
7. **No false production claim.** Check whether a new diagnostic type exists only in the probe or in production `Sources/`, whether `DocumentValidator` invokes it, and whether the GUI/CLI shares that Application Service path. Distinguish a proposed error ordering from a shipped contract. Do not claim performance or general safety from a fixed-case matrix.

## Acceptance boundary for this audit

The previous Spike proved that production accepts selected writes discarded by slot replacement and that naïve slot-wins or conflict-preflight can suppress `forbiddenOverride` and `conflictingVariants`. This audit must establish whether the new probe avoids those counterexamples without falsely rejecting dormant or disjoint writes, and whether any conclusion extends beyond the test-only evaluator into the production mutation and Canonical-save boundary.
